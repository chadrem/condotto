## Why this milestone (product thesis)

For Condotto to be viable it must support the Claude Code features that make the
implementer first-class (DESIGN §1 north-star). **Workflows — Claude Code's
multi-agent orchestration — are on that critical list.** M3.5 shipped per-session
model/effort and gated read-only subagents, but it **disabled the Workflow tool**
after a spike found its agents bypass our gate. This milestone gets workflows
working, integrated into the Slack UX, **secure by default, with an informed
insecure opt-in** — the architect (a software engineer) can knowingly trade safety
for capability, per thread. The architect is always the human in the loop; opting in
is theirs to do.

## The load-bearing finding from the M3.5 Workflow spike (READ THIS)

`spikes/m3.5/workflow-path.ts` ran the real Workflow tool through the real adapter +
policy engine on subscription auth. It found:

- The Workflow tool **is available** even under `settingSources: []`. The main
  agent's `Workflow` tool call (the launch) **hit our PreToolUse gate → allowed**.
- **BUT the workflow's orchestrated agents BYPASS the PreToolUse hook** — their tool
  calls carry **no `agent_id`** and never reach the `GateFn` (so the M3.5 subagent
  policy, which keys on `agentId`, never sees them). They instead **fall through to
  our `canUseTool` callback**, which is currently a blanket deny → so every workflow
  agent's Read AND Write was denied → workflows are non-functional.
- `enableWorkflows`/`disableWorkflows` are on the SDK **`Settings`** interface
  (loaded via `settingSources`), NOT query `Options`. We isolate with
  `settingSources: []`, yet the tool was still available (plan default).

**The opening:** `canUseTool` IS a real chokepoint that workflow-agent calls pass
through. Our security boundary just needs to move the policy there too. This is why
**secure read-only workflows are achievable** — not a security break.

**What Claude Code (the app) does, for framing:** the CLI lets workflow agents do
full read+write work, gated by its **interactive** permission prompts (a human
answering in real time, or `acceptEdits` auto-approving). Condotto can't do real-time
per-call prompts for a fleet of workflow agents over Slack, and per-write Slack
approvals across dozens of agents is impractical (the workflow would stall on human
latency). So Condotto reproduces the value as two modes: **read-only (gated via
`canUseTool`, needs no human)** by default, and an **informed worktree-write opt-in**
(the architect pre-authorizes worktree writes; the real review point is the land).

## Product decisions (locked in by the architect — build to these)

- **Write policy = read-only default + informed worktree-write opt-in ("Both").**
  Ship secure read-only workflows first; then a per-thread opt-in that lets workflow
  agents WRITE within the disposable worktree without per-write approval, with a
  clear warning.
- **Running UX = approve-launch + live status + final summary ("Both").** Architect
  approves the launch once; a single throttled status message updates while it runs;
  a summary posts at the end (what ran, key findings, cost).
- **Cost/scale = thread budget only.** No workflow-specific cap for now — the
  existing per-thread cost cap (`@Condotto budget`) + runaway pause is the brake.
  (Flag the tradeoff: one workflow can fan out hard and burn budget fast; make sure
  workflow spend is counted against the thread budget so the runaway pause can fire.)

## Spike FIRST (before building — this determines feasibility)

Like M0 and the M3.5 subagent spike: prove the mechanism before building on it. Add
`spikes/m3.6/` and log results in DECISIONS.md. Replace the blanket-deny `canUseTool`
with the real confinement policy (allow confined reads, deny the rest) and answer,
empirically, on live subscription auth against the throwaway testrepo:

1. Does `canUseTool` get called for **every** workflow-agent tool call, and does it
   receive the tool **input** (so we can check `file_path`/paths for confinement)?
2. If `canUseTool` **allows** confined reads, do workflow agents become **functional**
   (read/search/analyze in parallel) — and stay **confined** (out-of-worktree
   denied)? This is the make-or-break question for secure read-only workflows.
3. Does `canUseTool` also receive main-agent / `Agent`-subagent calls, or ONLY the
   "escaped" ones (batched main calls + workflow-agent calls)? Reads are normally
   shadowed from `canUseTool` by `allowedTools` — confirm that shadow does or doesn't
   apply to workflow agents (the M3.5 spike suggests their reads are NOT shadowed).
   This decides whether a policy in `canUseTool` disturbs the existing defer flow.
4. Confirm a workflow write can be **denied** via `canUseTool` (read-only default)
   and, separately, **allowed when worktree-confined** (for the write opt-in), and
   that out-of-worktree/credential writes stay hard-denied.
5. Sanity: does one `query()` running a workflow (many internal agents) behave under
   our turn/inactivity watchdog + the concurrency semaphore (one slot, N internal
   agents)? Note anything that needs handling.

If (2) holds, secure read-only workflows are real → build Tier 1. If not, record why
and fall back to the informed-insecure path only.

## Tiered plan (safest first, each independently demoable)

- **Tier 1 — Secure read-only workflows.** Re-enable the Workflow tool when
  workflows are on (un-disallow). Move the confinement policy into `canUseTool`:
  reuse the SAME core gate, but since `canUseTool` can't `defer`, map a `gate`
  decision to **deny** (so writes/bash/network from workflow agents are denied while
  confined reads are allowed). Keep the PreToolUse `defer` path unchanged for
  main-agent + `Agent`-subagent gated actions. **Verify the batching backstop still
  holds** — a batched main-agent write must still be denied by the new `canUseTool`
  policy (writes → gate → deny). Command: `@Condotto workflows on|off` (default off,
  architect-only), and re-fold workflows into `ultra` (= `xhigh` + subagents +
  workflows). Ports stay clean: `canUseTool` is adapter wiring; the decision is the
  core policy. Delivers: parallel read-only research/analysis/planning, gated +
  confined; the main agent still does writes via the approval loop.

- **Tier 2 — Slack UX for a running workflow (the "Both" choice).** (a) Gate the
  **launch**: the main agent's `Workflow` tool call is a gated action → post
  Approve/Deny in Slack showing what it will do (surface the workflow's
  `meta.name`/`description` from the tool input). (b) **While running**: a single
  throttled, trailing-flushed status message (reuse the M3 progress mechanism)
  showing phase/agent counts as they stream. (c) **On completion**: a terse summary
  (what ran, key findings/output, `total_cost_usd`). Make the turn watchdog and
  concurrency accounting tolerate a minutes-long workflow turn.

- **Tier 3 — Informed worktree-write opt-in (the "insecure but informed" mode).**
  `@Condotto workflows write on|off` (architect-only, default off). On enable, post a
  **mandatory clear warning**: "workflow agents (and batched calls) will WRITE inside
  this thread's disposable worktree WITHOUT per-write approval; blast radius = this
  worktree; out-of-worktree, credential, and production-data access stay hard-denied;
  land/deploy still require an Approve click — that's the review point." Implement by
  the gate allowing in-worktree writes/bash for this session (deny out-of-worktree /
  credentials / prod-data). The land/deploy approval + the diff the architect reviews
  before landing is the real safety net. Default OFF; the warning is non-skippable.
  Surface the mode in the settings announcement (`settingsBlock`) so it's always
  visible.

## Demo (defines done)

A PM asks for a cross-cutting job a single agent can't do well — e.g. "audit how we
handle auth across the codebase" or "research every place we call the payments API."
The architect approves launching a **workflow**; it fans out read-only across many
files in parallel and posts a synthesized, cited summary in the thread — gated and
worktree-confined the whole time. Then, optionally, the architect flips
`@Condotto workflows write on` (acknowledging the warning) and a workflow does a
parallel refactor within the worktree; the architect reviews the diff and approves
the land. All in Slack, on the throwaway repo.
